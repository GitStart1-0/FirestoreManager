# Специфікація Турнірних Питань Noesis (Tournament Questions Schema) — Версія 2.0 (Виправлена)

Цей документ визначає архітектуру, структуру даних та правила безпеки для турнірних питань у системі Noesis. Специфікація враховує вимоги масштабованості, захисту від витоку відповідей (Cheat Prevention), сумісності з Android-клієнтом та серверною логікою Cloud Functions.

---

## 1. Архітектурні Принципи та Уніфікація

### Відмова від річних та мовних колекцій
Замість створення динамічних колекцій на кшталт `ua_tournamentQuestions_2026` (що призводить до потреби у щорічному копіюванні даних, дублюванні індексів та ускладненні логіки запитів), використовується **єдина уніфікована колекція**:

```text
tournamentQuestionPools/{documentId}
```

Мова, категорія та сезонність визначаються виключно через атрибути документа.

### Інтерфейс Конструктора (Noesis Constructor UI)
Інтерфейс конструктора було повністю оновлено та адаптовано під версію 2.0:
* **Поле річної колекції** перетворено на `Рік / Сезон (seasonId)`. Це поле є опціональним і записується як атрибут документа (напр. `"2026"`), а не створює нову колекцію.
* **Назва колекції (автоматично)** змінена на фіксовану системну назву `tournamentQuestionPools`.
* Додано **динамічне відображення ключа швидкої індексації (`poolKey`)** безпосередньо під час редагування.
* Поле ліміту часу заблоковано на значенні `15` секунд для повної сумісності з Android-клієнтом та сервером.
* З умов безпеки та чистоти пулу прибрано зайві статуси на кшталт `draft` (публікуються лише готові питання зі статусом `active` або `disabled`).

### Спосіб публікації (Конструктор -> Cloud Function / Direct Secure Transaction)
Прямий запис із клієнтського конструктора у загальний пул питань турнірів **заборонений**.
1. Конструктор робить запит до захищеної Cloud Function: `publishTournamentQuestion(payload)`.
2. Функція виконує строгу валідацію полів на серверній стороні.
3. Функція генерує службові поля (`poolKey`, `randomKey`, `contentHash`, `publishedAt`, `publishedBy`) та записує документ.

## 2. Безпека та Захист від Чітерства (Security Rules)

Для запобігання витоку відповідей діє принцип **нульової видимості правильних відповідей на клієнті**. Клієнтська частина гри ніколи не завантажує документи з `tournamentQuestionPools` напряму.

### Правила безпеки Firestore (`firestore.rules`)
Пряме читання та запис клієнтами повністю заблоковані. Доступ має лише Admin SDK у Cloud Functions.

```javascript
match /tournamentQuestionPools/{questionId} {
  allow read, write: if false; // Повна ізоляція на рівні клієнтського SDK
}
```

### Захист від витоку відповідей та пояснень
* **Вирізання відповідей**: Серверна функція підготовки питання для раунду (`sanitizeTournamentQuestion`) видаляє поля `correctAnswer`, `correctAnswers` та `correctAnswerIndices` перед надсиланням клієнту.
* **Приховування пояснення (Explanation Reveal)**: Поле `explanation` **заборонено** надсилати клієнту разом із текстом питання. Воно надсилається клієнту **виключно після завершення раунду** (разом із верифікованою правильною відповіддю), оскільки текст пояснення часто містить пряму відповідь або підказку.

## 3. Схема Документа (Шляхи та Поля)

### Ідентифікатор Документа (`documentId`)
Для уникнення конфліктів синхронізації та приховування внутрішньої структури бази даних, як ID використовується **непрозорий хеш (SHA-256)** від комбінації початкового шляху та версії:
`SHA256(sourcePath + "_" + sourceVersion)` (наприклад, `d3b07384d113ed11aa...`).

### Спільні Поля Турнірного Документа

| Поле | Тип | Призначення | Опис / Обмеження |
| :--- | :--- | :--- | :--- |
| `language` | string | Мова питання | `"ua"`, `"de"`, `"en"` |
| `categoryId` | string | Ідентифікатор категорії | `"science"`, `"culture"`, `"erudite"`, `"philosophy"`, `"noesis"` |
| `type` | string | Тип питання для турніру | `"SINGLE_CHOICE"`, `"MULTIPLE_CHOICE"`, `"TRUE_FALSE"`, `"TEXT_INPUT"` |
| `poolKey` | string | Ключ швидкої індексації | Формат: `{language}\|{categoryId}\|{type}\|{difficulty}`. Використовується для миттєвої вибірки. |
| `question` | string | Текст запитання | Непорожній рядок, максимум 400 символів (для легкого читання на екрані смартфона). |
| `difficulty` | number | Складність (1–5) | Ціле число від 1 до 5. |
| `status` | string | Статус життєвого циклу | `"active"` або `"disabled"`. Чернетки (`draft`) не публікуються в пул. |
| `randomKey` | number | Випадковий маркер вибірки | Дійсне число `0 <= randomKey < 1` для рандомізації вибірки через `where('randomKey', '>=', cursor)`. |
| `seasonId` | string \| null | Прив'язка до сезону/року | `"2026"`, `"2027"` або `null` для безстрокових загальних питань. |
| `topicLabel` | string \| null | Назва теми для клієнта | Спрощена назва категорії, що відображається під час гри (напр., `"Астрономія"`). |
| `explanation` | string \| null | Пояснення до відповіді | Надсилається клієнту ТІЛЬКИ у фазі результатів раунду. |
| `timeLimitSeconds` | number | Ліміт часу на відповідь | За замовчуванням `15`. (Сумісно з константою Android-клієнта. Інші значення ігноруються до майбутніх оновлень). |
| `sourcePath` | string | Посилання на оригінал | Зберігається лише для внутрішньої аналітики та синхронізації. Ніколи не надсилається гравцям. |
| `sourceVersion` | number | Версія оригіналу | Версія питання на момент генерації дзеркала. |
| `schemaVersion` | number | Версія схеми турнірів | Поточне значення: `1`. |
| `contentHash` | string | Хеш текстового вмісту | Для запобігання дублюванню однакових за суттю питань. |
| `publishedAt` | timestamp | Дата публікації у пул | `FieldValue.serverTimestamp()` |
| `publishedBy` | string | ID автора (UID) | UID користувача-конструктора, який виконав публікацію. |

## 4. Специфікація Відповідей за Типами

### 1) `SINGLE_CHOICE`
* **`answers`**: Масив рядків (від 2 до 6 варіантів). Кожен варіант до 80 символів.
* **`correctAnswerIndices`**: Масив цілих чисел, який містить рівно **один** індекс.
```json
{
  "answers": ["Марс", "Земля", "Сатурн", "Венера"],
  "correctAnswerIndices": [2]
}
```

### 2) `MULTIPLE_CHOICE`
* **`answers`**: Масив рядків (від 2 до 6 варіантів).
* **`correctAnswerIndices`**: Масив індексів правильних відповідей (не порожній, значення унікальні та знаходяться в межах розміру масиву).
```json
{
  "answers": ["Варіант A", "Варіант B", "Варіант C", "Варіант D"],
  "correctAnswerIndices": [0, 2]
}
```

### 3) `TRUE_FALSE`
* Не містить масиву `answers` (клієнт локалізує варіанти "Так/Ні" самостійно).
* **`correctAnswer`**: Строго булеве значення (`true` або `false`).
```json
{
  "correctAnswer": true
}
```

### 4) `TEXT_INPUT`
* Не містить масиву `answers`.
* **`correctAnswers`**: Непорожній масив рядків прийнятних варіантів відповідей у нижньому регістрі без зайвих пробілів та спецсимволів (для полегшення автоматичної перевірки на сервері).
```json
{
  "correctAnswers": ["київ", "місто київ"]
}
```

## 5. Серверна Валідація (Cloud Function Validation Rules)

Перед записом документу в `tournamentQuestionPools`, Cloud Function повинна провести сувору валідацію:

1. **Загальні перевірки**:
   * Довжина `question` не повинна перевищувати 400 символів.
   * `difficulty` має бути цілим числом в діапазоні `[1, 5]`.
   * `language` має відповідати підтримуваним мовам (`ua`, `en`, `de`).
2. **Перевірка контенту відповідно до `type`**:
   * Для `SINGLE_CHOICE` та `MULTIPLE_CHOICE`:
     * Кількість елементів у `answers` від 2 до 6.
     * `correctAnswerIndices` містить лише унікальні валидні індекси.
     * Для `SINGLE_CHOICE` довжина `correctAnswerIndices` повинна дорівнювати строго 1.
   * Для `TRUE_FALSE`: `correctAnswer` має бути типу `boolean`.
   * Для `TEXT_INPUT`: `correctAnswers` має бути масивом рядків (мінімум 1 елемент), приведених до нижнього регістру.

## 6. Концепція Формування Набору Питань Турніру (Tournament Question Sets)

Для забезпечення стабільності гри під час активної сесії турніру, питання не вибираються "на льоту" під час кожного раунду. Замість цього використовується двохетапна схема.

### Етап 1: Статична генерація набору (Question Set)
При створенні турніру сервер генерує незмінний список питань та записує його в окремий захищений документ:
```text
tournamentQuestionSets/{tournamentId}
```

Алгоритм вибірки сервером:
1. Визначається необхідна кількість питань (наприклад, 20 питань) з рівномірним розподілом за категоріями (`categoryId`) та типами.
2. Виконується швидкий запит до пулу за допомогою `poolKey` та курсора `randomKey`:
   ```javascript
   firestore.collection('tournamentQuestionPools')
     .where('poolKey', '==', 'ua|science|SINGLE_CHOICE|2')
     .where('randomKey', '>=', Math.random())
     .limit(1)
   ```
3. Вибрані питання копіюються у масив `questions` всередині документа `tournamentQuestionSets/{tournamentId}`. Вміст записується у **повному обсязі** (включно з правильними відповідями), але сам документ `tournamentQuestionSets` є **абсолютно закритим на читання клієнтами**.

### Етап 2: Раунд гри
Під час кожного раунду клієнт взаємодіє з сервером через сесію турніру:
1. Сервер бере поточне питання за індексом раунду з приватного `tournamentQuestionSets/{tournamentId}`.
2. Сервер вирізає правильні відповіді та пояснення за допомогою функції `sanitize`.
3. Очищене питання відправляється гравцям.
4. Після завершення 15-секундного таймера сервер верифікує надіслані клієнтами відповіді та повертає правильний індекс/варіант разом із полем `explanation`.
